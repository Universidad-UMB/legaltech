# API-001 — Contrato HTTP del backend LegalTech (DEMO)

## 1. Propósito y jerarquía de fuentes

Este documento define decisiones, reglas y casos de uso de los recursos HTTP. El archivo `contratos/API-001.openapi.yaml` es la **fuente estructurada para rutas, request/response y códigos HTTP**. `SEC-001` rige permisos. `DOMAIN-001` y `DOM-ME-001` rigen precondiciones y transiciones. `DATA-001` rige integridad física. En caso de discrepancia, registrar un issue de contrato antes de codificar; **no resolver inventando comportamiento en el agente**.

**Alcance:** sólo el flujo del prototipo con datos sintéticos. El funcionamiento real de CPNU, SAMAI, Publicaciones Procesales, LLM, correo, PDF y programación masiva queda fuera.

## 2. Convenciones generales

- Prefijo `/api/v1` excepto `/healthz`; nombres de rutas en inglés y redacción documental en español.
- JSON UTF-8; fechas ISO 8601 con offset/UTC, UUID para referencias de API; el radicado del demo tiene 23 dígitos como cadena y no se convierte en número.
- Autenticación `Authorization: Bearer <opaque_token>` para todo excepto `POST /api/v1/auth/sessions` y `/healthz`. No se usan cookies ni refresh tokens en esta demo.
- Respuestas `Cache-Control: no-store` para autenticación y todo recurso sensible; `X-Request-ID` para correlación (generado por servidor si falta; no confiar en texto no validado).
- Rechazar campos ajenos al DTO (`extra=forbid`). No aceptar `actor_id`, `person_id`, `roles`, `tenant_id` ni `client_id` externos en operaciones del portal.
- Las lecturas internas deben aplicar permisos y asignación; sólo las rutas `internal` pueden aceptar `client_id` cuando la operación lo necesita y el servidor valida autorización.
- Listas con `limit` 1–100 (por defecto 25) y `cursor` opaco; orden estable `(created_at,id)` en dominio de lista. Nunca devolver filas de otros clientes.
- No exponer excepciones de SQLAlchemy, hashes, stack traces ni metadatos de autorización en el cuerpo. `problem+json` según RFC 9457. El agente deberá **sustituir los errores 422 predeterminados de FastAPI**, de ser necesario, para que el formato real coincida con el contrato.
- **Estados:** 201 creado, 200 resultado/lectura o repetición idempotente explícita, 204 logout; 401 credenciales/sesión inválida; 403 acción denegada por rol sin confirmar existencia; 404 recurso inaccesible o inexistente; 409 transición, duplicado no idempotente, conflicto de versión o concurrencia; 422 entrada sintáctica o semántica inválida; 429 protección de login; 500 error inesperado sanitizado.
- Sólo `POST acquisition-runs` admite `request_key` de cliente como clave de petición: misma clave + mismo proceso/fixture -> 200 mismo run; carga distinta -> 409; `UNIQUE(request_key)` debe aplicarse en DB. `POST comparisons` y `POST evaluations` usan unicidad de negocio y devuelven 200 para reintentos equivalentes; el resto de POST se valida por estado/duplicidad y puede devolver 409. No prometer infraestructura genérica de idempotency keys sin tabla adicional.

## 4. Flujos contractuales del prototipo

### F4-A. Registro y separación por cliente

- ADMIN crea Alfa/Beta, proceso `00000000000000000000001`, y seguimientos A/B y A2.
- El seed local aprovisiona las asignaciones internas y los ámbitos externos; no se expone endpoint de administración de cuentas/scopes en el primer incremento.
- `POST /trackings` necesita `client_id` sólo en operación interna autorizada. Una cuenta externa **nunca** puede pasarlo.
- ADMIN puede suspender/reactivar; ANALYST asignado puede finalizar cuando la política permite esa operación. Transacciones registran motivo y actor.

### F4-B. Observación, línea base y comparación

1. `POST /internal/acquisition-runs` con fixture `OBS_001` devuelve resultado SUCCESS y observación sellada con 5 actuaciones. Run con FAILED/INCOMPLETE conserva cobertura explícita, sin evidencia falsa de «sin cambios».
2. `POST /trackings/{id}/adoptions` para A establece su primera baseline. El servidor confirma `BASELINE_SET`; no genera novedad retrospectiva.
3. Segunda adquisición `OBS_002` registra 6 actuaciones; `POST /internal/comparisons` de OBS_001→OBS_002 devuelve cambio ADDED/ACT-06.
4. `POST /trackings/{A}/evaluations` comprueba elegibilidad y genera **una** novedad A. Si repite comparación/evaluación, se reutilizan identificadores; no se genera un segundo cambio/novedad.
5. B adopta OBS_002 como **primera** línea base; no obtiene novedad histórica por ACT-06.
6. **Precondición que debe especificarse en Fase 5:** no adelantar `last_adopted_observation_id` de un seguimiento más allá de la comparación pendiente sin evaluar cuando se espera crear una novedad. La implementación debe coordinar adopción/compare/evaluación para evitar perder eventos. Se propone conservar explícitamente observación previa o agrupar operación de avance en caso de uso; registrar en DEC-F4-001.

### F4-C. Tratamiento y publicación

1. ANALYST asignado inicia revisión; documenta evidencia y escala.
2. LAWYER asignado registra una valoración **humana ficticia**.
3. PREPARER asignado crea publicación y borrador, referencia la novedad del mismo seguimiento y registra su `person_id` a partir de sesión.
4. Someter congela la versión y marca `PENDING_APPROVAL`. No existe PATCH/PUT de contenido después de someter.
5. COORDINATOR asignado autoriza versión **si no es preparador por identidad de persona**, aun si dispone de otra cuenta.
6. Publicar significa: en **una sola transacción** marcar PUBLISHED, seleccionar `current_version_id` y registrar transición. Falla implica rollback completo y ninguna consulta externa confirma publicación.
7. Si cambia texto/destinatario/snapshot, se crea **otra versión** mediante `POST /publications/{publication_id}/versions` sin heredar aprobación. El destinatario en DEMO está fijado por el seguimiento de publicación, no es editable por cuerpo HTTP.

### F4-D. Portal

- `GET /portal/trackings` lista únicamente recursos del cliente asociado a la sesión, con ámbito explícito y estados permitidos.
- `GET /portal/trackings/{id}/current-publication`: si hay permiso y seguimiento ACTIVO pero no versión publicada, devuelve `200` con `available=false`, `publication=null` y cobertura real; jamás contenido de borrador.
- Recurso ajeno, seguimiento finalizado, falta de ámbito y cliente suspendido devuelven **404 genérico** para lectura por ID. Nunca confirmar que el recurso existe o pertenece a Alfa/Beta.
- Un estado de fuente FAILED/INCOMPLETE se expone como estado de cobertura en un recurso **ya autorizado**; no se interpreta como cero cambios.
- Suspensión/finalización no borra versión ni revoca necesariamente sesión: revoca **permiso ordinario de consulta** y se reevalúa en cada lectura.

## 5. Respuestas ilustrativas (no evidencias de ejecución)

**Sin publicación todavía** de un seguimiento autorizado: `200`:

```json
{{"available":false,"coverage_status":"COMPARABLE","publication":null}}
```

**Ausencia o ámbito denegado**: `404` con media type `application/problem+json`:

```json
{{"type":"about:blank","title":"Not Found","status":404,"detail":"Recurso no disponible","request_id":"11111111-1111-4111-8111-111111111111"}}
```

**Invalidez de sesión** `401` indistinta por expiración, revocación o token desconocido. **Negación por rol** `403` sólo cuando la operación en abstracto no está permitida, sin consultar si el ID existe. **Transición inválida** `409` cuando el actor ya tiene autorización sobre el recurso y se puede explicar el conflicto sin fuga.

## 6. Relación con modelos de persistencia

La API no permite editar ni eliminar observaciones selladas, cambios, revisiones previas, versiones congeladas o auditoría. Los endpoints de mutación usan un solo Unit of Work y los conflictos de unicidad requieren rollback y nueva transacción antes de relectura. Los recursos públicos se seleccionan mediante consultas que incluyan ámbito, cliente y seguimiento; las FKs **no sustituyen** autorización.

## 7. Exclusiones y compatibilidad

- No hay refresh tokens, OIDC, pagos, notificaciones, CRUD de `accounts` ni administración de scopes por la API.
- No se implementará `POST /demo/reset`; seed y reinicio pertenecen a comandos CLI expresamente restringidos a `DEMO` y base descartable.
- No introducir `PATCH` genérico de estados ni detalles de triggers al cliente.
- No se declara seguridad para despliegue público o cumplimiento normativo con información judicial real.

## 8. Aceptación del contrato

Validez sintáctica del OpenAPI, referencias resolubles, 35 operationId únicos, respuestas de error estándar, roles y ámbito documentados, ruta trazada a los 18 AT y verificación futura de que `/openapi.json` de FastAPI no contradiga el contrato aprobado. El contrato es diseño candidato hasta aceptación de los autores.
