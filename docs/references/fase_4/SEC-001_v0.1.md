# SEC-001 — Modelo de autenticación, autorización y seguridad

## 1. Activos y amenazas prioritarias

**Activos:** credenciales de prueba, tokens de sesión, ámbitos externos, seguimientos internos, observaciones, novedades, decisiones jurídicas, versiones aprobadas y auditoría. **Amenazas:** BOLA/IDOR, elevación de rol, acceso cruzado Alfa/Beta, acceso de A sin ámbito A2, sesión caducada/revocada, mass assignment, replay/duplicado, fuerza bruta contra login, aprobación por dos cuentas de la misma persona, edición posterior a aprobación y fuga por errores/logs. **Datos:** exclusivamente sintéticos; usar datos reales requerirá nueva revisión legal y de seguridad.

## 2. Autenticación DEMO

- Contraseñas con **Argon2id**, sal aleatoria y parámetros de biblioteca mantenida; nunca texto plano en BD, logs ni fixtures de producción.
- `POST /api/v1/auth/sessions`: validar username normalizado + contraseña, devolver token **aleatorio criptográfico** con al menos 256 bits de entropía, formato opaco. Guardar únicamente `SHA-256(token)` (32 bytes) en `auth_sessions` con cuenta, emisión, expiración, revocación.
- Vigencia absoluta candidata: **60 minutos**. Sin refresh, sin sliding expiration. Cuenta DISABLED o sesión revocada/expirada → 401. Cerrar sesión marca revocación.
- Token en `Authorization: Bearer`. Para la demo web se recomienda guardarlo **en memoria de la aplicación**, no en `localStorage`, URL ni cookie; al recargar se inicia sesión nuevamente. Esto no elimina riesgo XSS; el cliente no debe insertar contenido no confiable en HTML sin escape.
- Sin cookie de autenticación, CSRF por cookie de sesión no aplica a este contrato; si el equipo migra a cookies deberá diseñar defensa CSRF y actualizar OpenAPI/ADR.
- Desarrollo HTTP permitido **sólo en localhost**. Para red externa HTTPS obligatorio y despliegue fuera de alcance de esta versión. CORS cerrado por defecto; orígenes de desarrollo definidos mediante lista exacta, sin credenciales/cookies y sin origen `*` para entornos no locales.
- Limitar login con control de tasa en entorno de un solo proceso y respuestas genéricas; no asumir que un contador en memoria sirve para varios workers o producción. Test de ráfagas y 429.

## 3. Identidad efectiva y alcance

`Principal` se resuelve **en cada petición**: token digest vigente, cuenta activa, persona vinculada, roles actuales, `client_id` externo si existe. Los roles no se toman de peticiones. `Authorize` combina rol, asignación interna revocable o scope externo revocable, existencia y pertenencia del recurso, estado actual del cliente y del seguimiento, y estado de la versión. **Deny by default**.

`✓` es elegibilidad por rol **más** autorización contextual, no privilegio universal. El usuario ADMIN no evita restricciones de persona preparadora, tenant o estados. Para simplificar el primer incremento, las asignaciones internas, cuentas y scopes se crean mediante **seed local**, no vía API. No se simula una administración productiva de usuarios.

## 4. Secuencia de autorización por recurso

1. Resolver sesión y principal válidos.
2. Validar permiso de **acción** (sin revelar recurso). Si no existe → `403`.
3. Consultar recurso con filtro de asignación/cliente/ámbito; no buscar por ID desnudo y devolver detalles después.
4. Comprobar estado actual (cliente/seguimiento/versión); solicitud externa fuera de ámbito, suspendida o finalizada → `404` genérico.
5. Ejecutar operación con guardas del dominio. Mutaciones: verificar autorizaciones y estado bajo misma transacción y bloqueo cuando corresponda.
6. Auditar resultado sin token, contraseñas, descripción de actuaciones ajenas ni datos de cliente no autorizado.

La autorización externa por `client_id` enviado es imposible por contrato: el cliente se obtiene de `Principal` y la relación asignada. Dentro de un mismo cliente, la cuenta A sin scope A2 tampoco podrá leer A2. El acceso a proceso compartido **no** otorga acceso a novedad/publicación ajena.

## 5. Errores y mitigación de enumeración

| Situación | HTTP | Regla |
|---|---|---|
| Usuario/contraseña incorrectos | 401 | Mensaje genérico, sin distinguir cuenta existente |
| Sesión ausente, inválida, expirada, revocada | 401 | Sin revelar causa exacta |
| Rol no habilita una operación | 403 | Denegar antes de consultar existencia del recurso |
| ID inexistente / recurso ajeno / cliente suspendido / seguimiento finalizado en portal | 404 | Cuerpo uniforme sin detalles de pertenencia |
| Operación autorizada en estado incorrecto | 409 | Respuesta de negocio, sin detalles internos |
| Campos inválidos | 422 | Mensaje de validación sanitizado |
| Exceso login | 429 | Mensaje genérico y `Retry-After` donde aplique |
| Fallo de BD/servidor | 500 | `request_id` para localizar diagnóstico sin stack trace |

Evitar diferencias significativas en cuerpo y encabezados para `404` ajeno/inexistente. Las diferencias de tiempos pueden requerir evaluación futura; no prometer indistinguibilidad criptográfica.

## 6. Protección de publicación y separación de personas

- El servidor vincula preparadores a `person_id`, no a un `username` de pantalla.
- COORDINATOR debe tener asignación y persona diferente de **toda** la lista de preparadores de la versión.
- Revisión jurídica humana anterior obligatoria en la **demo**, propuesta DEC-08 no ratificada.
- Un cambio a cuerpo, destinatario o conjunto de novedades produce nueva versión; la aprobada sigue inmutable. Se comprueba `content_sha256` y estado al aprobar/publicar.
- Selección de versión pública y transición a PUBLISHED se confirman en un mismo commit. Error/rollback no debe exponer versión parcial.
- Suspensión o cierre impide nuevas lecturas ordinarias tras confirmar el cambio, aunque el registro de publicación siga `PUBLISHED` internamente. No prometemos retirar retroactivamente contenido ya descargado.

## 7. Auditoría y observabilidad

Registrar `request_id`, tipo de evento, actor (si autenticado), recurso autorizado, resultado, fecha UTC, y razón sanitizada. No registrar bearer tokens, body de login, hashes de contraseña, contenido de comunicaciones ni identificadores de recursos ajenos en eventos de denegación. Cambios exitosos y transiciones en la misma transacción que el estado; denegaciones/errores pueden necesitar UoW aislado para persistir aun cuando el principal se revierta. Documentar si el registro de auditoría falla; para mutaciones críticas, fallo de auditoría transaccional impide declarar éxito.

## 8. Seguridad y límites de despliegue

Entorno local de demo con cuentas ficticias. Secretos por variables de entorno **no versionadas**; `.env.example` solo valores de ejemplo no operativos. PostgreSQL no expuesto innecesariamente; usuarios de DB sin privilegios de DDL para runtime. Backup real, cumplimiento de privacidad, SSO, RLS, WAF, MFA, HA, pentest y retención regulatoria no se certifican en demo. Aun así, tests negativos de autorización son obligatorios.
